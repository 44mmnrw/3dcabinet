# 📌 Система версионирования проекта 3DCabinet

## 🎯 Общие принципы

Проект использует **семантическое версионирование (Semantic Versioning)** в формате `MAJOR.MINOR.PATCH`:

- **MAJOR** — несовместимые изменения API/структуры
- **MINOR** — новая функциональность с обратной совместимостью
- **PATCH** — исправления ошибок, мелкие улучшения

## 📦 Версионирование компонентов

### 1. Основной проект (package.json)

**Файл**: `package.json`

```json
{
  "version": "1.0.0"
}
```

**Правила обновления**:
- Обновляется при значительных изменениях в проекте
- Синхронизируется с релизами на GitHub
- Используется для npm-пакетов (если проект будет опубликован)

**Примеры**:
- `1.0.0` → `1.0.1` — исправление бага
- `1.0.1` → `1.1.0` — добавлена новая функция
- `1.1.0` → `2.0.0` — кардинальные изменения архитектуры

---

### 2. Python-скрипты (tools/)

**Формат**: Константы в начале файла

```python
# Метаданные скрипта
SCRIPT_VERSION = "2.0.0"
SCRIPT_DATE = "2025-11-16"
SCRIPT_AUTHOR = "3DCabinet Team"
```

**Файлы**:
- `tools/generate-cabinet-class.py` — генератор классов шкафов
- `tools/freecad/export_to_threejs.py` — экспорт из FreeCAD
- Другие утилиты в `tools/`

**Правила обновления**:
- **MAJOR** — изменение формата входных/выходных данных, API скрипта
- **MINOR** — добавление новых функций, опций
- **PATCH** — исправление багов, улучшение обработки ошибок

**Примеры**:
- `1.0.0` → `1.0.1` — исправлена ошибка парсинга JSON
- `1.0.1` → `1.1.0` — добавлена поддержка новых форматов
- `1.1.0` → `2.0.0` — изменена структура выходных файлов

**Дата**: Формат ISO `YYYY-MM-DD` для удобства сортировки

---

### 3. TypeScript/JavaScript модули

**Формат**: JSDoc комментарии или константы

```typescript
/**
 * Модуль управления шкафами
 * @version 1.2.0
 * @date 2025-11-16
 */
export class CabinetManager {
    // ...
}
```

**Правила обновления**:
- Обновляется при изменении публичного API класса/модуля
- Можно использовать для внутренних модулей, но не обязательно

**Рекомендация**: Для внутренних модулей версионирование опционально, достаточно git-истории.

---

### 4. База данных (миграции Laravel)

**Формат**: В имени файла миграции

```
2025_11_16_082610_create_cabinets_table.php
```

**Правила**:
- Дата в формате `YYYY_MM_DD_HHMMSS`
- Автоматически генерируется Laravel
- Версия схемы БД = последняя миграция

---

### 5. Документация (README, MD-файлы)

**Формат**: В конце файла или в заголовке

```markdown
**Версия**: 2.0.0  
**Дата**: 2025-11-16  
**Автор**: 3DCabinet Team
```

**Правила обновления**:
- Обновляется при значительных изменениях документации
- Дата обновления обязательна

## 🔄 Процесс обновления версий

### При коммите изменений:

1. **Определите тип изменения**:
   - 🐛 **PATCH** — исправление бага
   - ✨ **MINOR** — новая функция
   - 💥 **MAJOR** — breaking changes

2. **Обновите версию**:
   ```python
   # Было: SCRIPT_VERSION = "1.0.0"
   # Стало: SCRIPT_VERSION = "1.0.1"  # для бага
   ```

3. **Обновите дату**:
   ```python
   SCRIPT_DATE = "2025-11-16"  # Текущая дата
   ```

4. **Добавьте в коммит**:
   ```bash
   git add tools/generate-cabinet-class.py
   git commit -m "fix: исправлена ошибка парсинга размеров (v1.0.1)"
   ```

## 📋 Чеклист версионирования

### При добавлении новой функции:
- [ ] Обновить `MINOR` версию (1.0.0 → 1.1.0)
- [ ] Обновить дату
- [ ] Обновить CHANGELOG (если есть)
- [ ] Обновить документацию

### При исправлении бага:
- [ ] Обновить `PATCH` версию (1.0.0 → 1.0.1)
- [ ] Обновить дату
- [ ] Добавить описание исправления в коммит

### При breaking changes:
- [ ] Обновить `MAJOR` версию (1.0.0 → 2.0.0)
- [ ] Обновить дату
- [ ] Обновить документацию с описанием изменений
- [ ] Добавить миграцию (если нужно)

## 🏷️ Теги Git (рекомендуется)

Для важных релизов создавайте теги:

```bash
# Создать тег
git tag -a v1.0.0 -m "Релиз версии 1.0.0"

# Отправить теги на сервер
git push origin v1.0.0
```

**Формат тегов**: `vMAJOR.MINOR.PATCH` (например, `v1.0.0`)

## 💡 Рекомендации

1. **Не переусердствуйте**: Версионируйте только важные компоненты
   - ✅ Скрипты-утилиты (`tools/`)
   - ✅ Основной проект (`package.json`)
   - ❌ Временные скрипты, тесты

2. **Используйте git**: Для большинства файлов достаточно git-истории
   - Версионирование нужно для:
     - Публичных API
     - Утилит, используемых другими разработчиками
     - Документации

3. **Синхронизируйте**: Если компоненты связаны, обновляйте версии вместе
   - Например, если генератор классов изменился, обновите документацию

4. **Дата важнее версии**: Для внутренних инструментов дата обновления часто важнее номера версии
